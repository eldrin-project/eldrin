# **Technical Architecture and Implementation Guide for the Romanian RO e-Factura System**

## **Executive Summary**

The digitization of fiscal administration represents one of the most significant structural shifts in the European economic landscape, with Romania taking a decisive lead through the implementation of the RO e-Factura system. This report provides an exhaustive technical analysis and implementation roadmap for software architects, developers, and systems integrators tasked with connecting to the Romanian National Agency for Fiscal Administration (ANAF).

The RO e-Factura system marks a fundamental transition from a retrospective, post-audit tax model—where invoices are issued directly between parties and audited later—to a continuous transaction control (CTC) clearance model. In this ecosystem, an invoice is only considered legally valid for Value Added Tax (VAT) deduction purposes once it has been transmitted to ANAF, validated against the RO-CIUS (Core Invoice Usage Specification) standards, and digitally sealed by the tax authority.1 This shift necessitates a paradigm change in enterprise resource planning (ERP) and billing software design, moving from asynchronous, document-centric workflows to synchronous, data-centric interactions with government infrastructure.

This document details the end-to-end integration lifecycle, covering the mandatory legislative framework, the cryptographic prerequisites for access, the intricate OAuth 2.0 authentication flow, the granular structure of UBL 2.1 XML data models, and the specific RESTful API endpoints required for submission and retrieval. Furthermore, it addresses the critical expansion of the system to Business-to-Consumer (B2C) transactions effective January 1, 2025, providing the necessary technical specifications to handle personal identification data in compliance with both fiscal mandates and GDPR privacy standards.3

## **1\. The Regulatory and Technical Landscape**

### **1.1 The Shift to Electronic Clearance**

To understand the technical requirements of RO e-Factura, one must first comprehend the regulatory intent driving the architecture. Romania has historically faced the largest VAT gap in the European Union, a metric representing the difference between expected VAT revenue and the amount actually collected.5 To combat tax evasion and increase transparency, the government, authorized by the EU Council Implementing Decision 2023/1553, introduced a mandatory electronic invoicing system that acts as a real-time ledger of economic activity.6

For the technical architect, this implies that the "Invoice" entity in any database can no longer be treated as a final, immutable record upon generation. Instead, an invoice exists in a "Draft" or "Pending" state until the external system (ANAF) confirms its validity. The integration layer must therefore function as a gateway, blocking the finalization of financial periods or the distribution of invoices to customers until the ANAF digital seal is obtained. This creates a hard dependency on external API availability, necessitating robust fallback, queuing, and retry mechanisms within the application logic.

### **1.2 Standards: EN 16931 and RO-CIUS**

The technical backbone of the system is the European standard EN 16931, which was developed to harmonize electronic invoicing across member states. However, the standard allows for "Core Invoice Usage Specifications" (CIUS)—national or sectoral restrictions that define how the general standard applies in a specific context.

Romania's implementation, RO-CIUS, is rigorous. While the underlying format is UBL 2.1 (Universal Business Language) ISO/IEC 19845:2015, a generic UBL 2.1 file generated by an international ERP system will likely fail validation if it does not strictly adhere to RO-CIUS business rules.1 These rules govern:

* **Mandatory Fields:** Elements that are optional in standard UBL (e.g., Buyer VAT ID for simplified invoices) may be mandatory in RO-CIUS.  
* **Code Lists:** The use of specific ISO codes for currencies (ISO 4217), units of measure (UN/ECE Recommendation 20), and country codes (ISO 3166-1 Alpha-2).  
* **Tax Categories:** Strict mapping of VAT rates to specific category codes (e.g., 'S' for Standard 19%, 'Z' for Zero-rated).

The system technically supports both UBL 2.1 and Cross Industry Invoice (CII) syntaxes, but UBL 2.1 is the overwhelming standard for implementation and documentation references.7

### **1.3 Implementation Timeline and Scope**

The rollout has been phased, adding complexity to legacy system support. Developers must account for different validation rules based on the transaction date and type:

* **Phase 1 (July 2022):** Mandatory for B2G (Business to Government) and high-risk B2B sectors (e.g., vegetables, alcohol, construction, mineral products).8  
* **Phase 2 (January 2024):** Generalized B2B mandate for all taxable persons established in Romania. This includes non-resident entities registered for VAT purposes in Romania.9  
* **Phase 3 (July 2024):** Strict enforcement with fines. The specific "grace period" allowed explicitly for no penalties ended here, shifting the operational risk to the technical teams maintaining these integrations.4  
* **Phase 4 (January 2025):** Mandatory reporting for B2C transactions. This massive expansion requires systems to differentiate dynamically between corporate and individual clients to apply the correct XML schema rules (e.g., handling CNP vs CUI).3

## **2\. Access Prerequisites and Digital Identity**

Accessing the RO e-Factura API is not merely a matter of obtaining an API key. It involves a rigorous identity verification process rooted in the eIDAS regulation for electronic identification. The security model relies on a chain of trust starting from a physical person and extending to the software application.

### **2.1 The Qualified Electronic Signature**

The foundation of authentication is the **Qualified Digital Certificate**. Unlike simple SSL certificates used for website encryption, this is a legal identity document for a natural person, issued by a Qualified Trust Service Provider (QTSP) accredited in Romania (e.g., CertSIGN, DigiSign, Trans Sped, AlfaTrust).11

* **Physical Token:** Typically, this certificate is stored on a cryptographic USB token (smart card). This presents the first major hurdle for automation: the private key cannot easily be extracted or installed on a cloud server.  
* **SPV Registration:** The individual holding the certificate must register in ANAF’s Virtual Private Space (Spațiul Privat Virtual \- SPV). Crucially, this individual must be linked to the company (Legal Entity) they wish to represent. They must hold rights as a **Legal Representative**, **Designated Representative**, or **Authorized Representative**.12  
* **One-to-Many Relationship:** A single digital certificate (and thus a single human user) can be authorized to represent multiple companies. The API handles this by requiring the specific tax identification number (CIF) of the company to be passed as a parameter in upload requests, but the authentication token represents the human user.7

### **2.2 Registering the Application (OAuth Client)**

To enable server-to-server communication without requiring the human user to be present for every transaction, ANAF utilizes the OAuth 2.0 protocol. However, the initial setup requires manual intervention.

The developer must register their application within the ANAF portal to obtain the Client ID and Client Secret.

1. **Portal Navigation:** The user logs in to www.anaf.ro using their digital certificate.  
2. **Developer Area:** Navigate to **Servicii Online** \> **Înregistrare utilizatori** \> **DEZVOLTATORI APLICAȚII**.11  
3. **Application Metadata:**  
   * **Application Name:** A recognizable name (e.g., "Company X ERP Integration").  
   * **Callback URL (Redirect URI):** This is the most critical technical parameter. It is the endpoint on *your* application where ANAF will return the user after they authorize access. For development and testing, ANAF accepts http://localhost or http://localhost:\[port\]. For production, this must be a secure public HTTPS URL.14  
   * **Service Scope:** Select access to "e-Factura" and "e-Transport" services.  
4. **Credential Issuance:** Upon saving, the portal displays the Client ID and Client Secret. These distinct strings are the credentials for the application itself, not the user.

### **2.3 The Sandbox (Test) Environment**

ANAF provides a dedicated testing environment, mirroring the production API but operating on a separate database.

* **No Separate Registration:** Unlike many modern SaaS platforms, there is no separate "Sandbox Account". The access is controlled by the same digital certificate and SPV registration. The differentiation occurs strictly at the **API Endpoint Level**.15  
* **Base URL:** The test environment is located at https://api.anaf.ro/test/FCTEL/rest/.  
* **Data Persistence:** Invoices sent to the test environment are validated and processed, generating a test signature. They do *not* affect the legal tax liability of the company. However, developers should be aware that the test environment often shares the same authentication server (logincert.anaf.ro) as production.13  
* **Limitations:** The test environment may have different uptime guarantees and may periodically be wiped or reset. It is intended for connectivity and syntax validation, not for long-term data archival testing.16

## **3\. Authentication Architecture: OAuth 2.0 Implementation**

The integration relies on the OAuth 2.0 Authorization Code Grant flow (RFC 6749). This flow is designed to exchange the user's high-security credential (the physical USB token presence) for a machine-usable credential (the Access and Refresh tokens).

### **3.1 Step 1: User Authorization (Browser-Based)**

The authentication sequence *must* begin in a web browser. The application cannot programmatically simulate the insertion of a USB token and the entry of a PIN.

Request Structure:  
The application directs the user's browser to the ANAF authorization endpoint.

* **URL:** https://logincert.anaf.ro/anaf-oauth2/v1/authorize 17  
* **Method:** GET  
* **Parameters:**  
  * response\_type: Set to code.  
  * client\_id: The ID obtained during app registration.  
  * redirect\_uri: The URL encoded Callback URL (must match registration exactly).  
  * scope: (Optional) token.  
  * state: A random, non-guessable string generated by the application. This is essential for security to prevent Cross-Site Request Forgery (CSRF) attacks. The application should store this state and verify it when the callback is received.18

**User Interaction:**

1. The user sees the ANAF login screen.  
2. They select the "Certificat Digital" option.  
3. The browser prompts for the certificate (interacting with the USB token driver).  
4. The user enters their PIN.  
5. ANAF validates the certificate against the SPV database.  
6. ANAF redirects the browser back to the redirect\_uri with a code and the state parameter.

### **3.2 Step 2: Token Exchange (Server-Side)**

The code received in the callback is short-lived (typically valid for a few minutes). The application backend must immediately exchange it for tokens.

**Request Structure:**

* **URL:** https://logincert.anaf.ro/anaf-oauth2/v1/token 17  
* **Method:** POST  
* **Headers:**  
  * Content-Type: application/x-www-form-urlencoded  
* **Body:**  
  * grant\_type: authorization\_code  
  * code: The authorization code received in the callback.  
  * client\_id: Your application's Client ID.  
  * client\_secret: Your application's Client Secret.  
  * redirect\_uri: The same URI used in step 1\.

Response Payload:  
The server responds with a JSON object containing:

* access\_token: A JWT (JSON Web Token) used to authorize API calls. Validity is typically short (e.g., 60 minutes).11  
* refresh\_token: A long-lived opaque string used to generate new access tokens.  
* expires\_in: Time in seconds until the access token expires.  
* token\_type: Bearer.

### **3.3 Step 3: Token Lifecycle Management (Refresh)**

To maintain an automated connection (e.g., a nightly batch upload) without requiring the user to re-insert their USB token every hour, the application must implement a robust refresh strategy.

**Refresh Request:**

* **URL:** https://logincert.anaf.ro/anaf-oauth2/v1/token  
* **Method:** POST  
* **Body:**  
  * grant\_type: refresh\_token  
  * refresh\_token: The stored refresh token.  
  * client\_id: Your Client ID.  
  * client\_secret: Your Client Secret.

**Operational Strategy:**

* **Proactive Refresh:** Do not wait for a 401 Unauthorized error. Track the expires\_in time and refresh the token when 5-10 minutes remain.  
* **Refresh Token Rotation:** Depending on ANAF's specific implementation updates, using a refresh token might result in a *new* refresh token being issued in the response. The application must always save the new values returned by the token endpoint, replacing the old ones.19  
* **Persistence:** Tokens should be stored securely (encrypted at rest) in a database, associated with the specific company (CIF) they authorize.  
* **Expiration:** If the refresh token itself expires (typically after 90 days of inactivity, or if revoked), the entire flow must restart from Step 1 (User Authorization).

## **4\. The Data Model: UBL 2.1 and RO-CIUS**

The heart of the integration is the generation of the XML file. This is where most integration errors occur. The file must be valid against the UBL 2.1 schema *and* the RO-CIUS business rules.

### **4.1 File Structure Overview**

A compliant invoice is an Invoice element in the namespace urn:oasis:names:specification:ubl:schema:xsd:Invoice-2.

| Section | Key Elements | RO-CIUS Requirement |
| :---- | :---- | :---- |
| **Header** | ID, IssueDate, InvoiceTypeCode, DocumentCurrencyCode | InvoiceTypeCode must be 380 (Invoice) or 381 (Credit Note). Currency must be RON for domestic tax reporting, though foreign currency is allowed if tax conversion is provided. |
| **Supplier** | AccountingSupplierParty | Must contain the PartyTaxScheme with TaxScheme/ID \= 'VAT' and the company's RO VAT code. Address fields must use RO county codes (e.g., RO-B for Bucharest, not "Sector 1"). |
| **Customer** | AccountingCustomerParty | For B2B: Valid VAT code. For B2C: specific flagging for non-taxable persons (see Section 6). |
| **Lines** | InvoiceLine | Each line must have an InvoicedQuantity (with Unit Code), LineExtensionAmount (Net Value), and Item/ClassifiedTaxCategory (VAT rate). |
| **Tax Total** | TaxTotal | Must be calculated accurately per VAT category. Rounding errors here are the most common cause of rejection. |

### **4.2 Critical Data Fields and Constraints**

#### **4.2.1 Identity and Addressing**

ANAF validates the consistency of the VAT ID (CIF) against the address. The PostalAddress element is strictly validated.

* **CityName:** While this is a text field, it should align with official nomenclature to ensure smooth processing.20  
* **CountrySubentity:** This field represents the County (Județ). RO-CIUS mandates the use of the ISO 3166-2:RO codes (e.g., RO-CJ for Cluj, RO-CT for Constanța). Using full names like "Cluj" or "Cluj-Napoca" in this specific code field will cause validation failure.

#### **4.2.2 VAT Categories (TaxScheme)**

Every line item must associate a VAT rate with a category code. Common mappings include:

* **S (Standard):** 19% VAT.  
* **Z (Zero-rated):** 0% (e.g., intra-community supply).  
* **E (Exempt):** Tax exempt services.  
* **O (Outside scope):** Not subject to VAT.

If a code other than 'S' is used, the XML often requires a TaxExemptionReason or TaxExemptionReasonCode to explain the deviation, citing the specific article of the Fiscal Code.21

#### **4.2.3 Totals and Rounding**

The XML must contain a LegalMonetaryTotal section summing up the invoice.

* **TaxInclusiveAmount:** Total with VAT.  
* **TaxExclusiveAmount:** Total net base.  
* PayableAmount: The final amount to be paid.  
  ANAF's validator performs a mathematical check: LineExtensionAmount \* VAT Rate vs. TaxAmount. Differences caused by line-level rounding vs. total-level rounding can lead to rejections. The standard generally recommends line-level calculation summed up, but consistency is key.

## **5\. API Architecture and Interaction Flow**

The interaction with ANAF is **asynchronous**. You cannot upload an invoice and immediately get a success confirmation. The process is a state machine moving through: Upload \-\> Processing \-\> Ready.

### **5.1 Endpoint 1: Upload (Submission)**

This endpoint accepts the XML file and places it in the processing queue.

* **Production URL:** https://api.anaf.ro/prod/FCTEL/rest/upload  
* **Test URL:** https://api.anaf.ro/test/FCTEL/rest/upload 7  
* **Method:** POST  
* **Authentication:** Authorization: Bearer \<access\_token\>  
* **Parameters (Query String):**  
  * standard: UBL (Standard format).  
  * cif: The VAT number of the **Supplier** (Issuer). This allows ANAF to route the file to the correct SPV account even if the authenticated user represents multiple companies.  
  * extern: DA (Use only if the supplier is non-resident).  
  * autofactura: DA (Use only for self-billing scenarios).  
* **Body:** The raw binary content of the XML file.

**Response (Synchronous):**

* **HTTP 200 OK:**  
  * JSON Body: {"id\_incarcare": "12345678"}.  
  * **Crucial Insight:** This id\_incarcare (Upload Index) is *not* the Invoice ID. It is merely a "Ticket ID" for the processing queue. The application must save this ID to check the status later.14  
* **HTTP 400 Bad Request:** Immediate failure (e.g., malformed XML, invalid CIF).  
* **HTTP 403 Forbidden:** The OAuth token is valid, but the user does not have rights for the cif specified in the URL.

### **5.2 Endpoint 2: Status Checking (Polling)**

After upload, the file undergoes asynchronous validation (syntax check, semantic check, business rule check).

* **URL:** https://api.anaf.ro/\[prod|test\]/FCTEL/rest/stareMesaj  
* **Method:** GET  
* **Parameters:**  
  * id\_incarcare: The ID received from the Upload endpoint.

**Response States:**

1. **State: "in prelucrare" (Processing):** The system is still analyzing the file.  
   * *Strategy:* Wait and retry. Implement an exponential backoff (e.g., wait 5s, then 10s, then 30s) to avoid hitting rate limits (HTTP 429).  
2. **State: "nok" (Not OK):** Validation failed.  
   * *Payload:* The response will contain an array of error messages explaining strictly why the XML was rejected (e.g., "Invalid VAT calculation on line 3").  
   * *Action:* Map these errors to user-friendly messages and display them in the ERP interface for correction.  
3. **State: "ok" (Valid):** Success.  
   * *Payload:* {"stare": "ok", "id\_descarcare": "99887766"}.  
   * *Action:* The id\_descarcare (Download ID) allows retrieval of the final sealed document.14

### **5.3 Endpoint 3: Download (Retrieval)**

This step is legally mandatory. The "Invoice" is not valid until you possess the ANAF-sealed version.

* **URL:** https://api.anaf.ro/\[prod|test\]/FCTEL/rest/descarcare  
* **Method:** GET  
* **Parameters:**  
  * id: The id\_descarcare.

**Response:**

* **Content-Type:** application/zip  
* **Contents:** A ZIP archive containing:  
  1. signature.xml: The digital signature applied by the Ministry of Finance.  
  2. invoice.xml: The original UBL XML.  
* **Archiving:** The application must extract and store this ZIP file (or the combined signed XML) for the statutory period of 10 years. This file serves as the only legal proof of the invoice existence for VAT deduction.7

### **5.4 Utility Endpoint: XML to PDF**

Since XML is not human-readable, ANAF provides a conversion service to generate a visualization.

* **URL:** https://api.anaf.ro/\[prod|test\]/FCTEL/rest/transformare/FACT1/DA 22  
* **Method:** POST  
* **Body:** XML Content.  
* **Response:** PDF file stream.  
* **Usage:** Useful for emailing a "Courtesy Copy" to clients or for internal document management visualization. Note that the PDF is *not* the legal invoice; the XML is.

## **6\. Business-to-Consumer (B2C) Integration Specifics**

Effective January 1, 2025, the scope expands to B2C transactions. This creates significant data privacy (GDPR) and technical challenges regarding the "Customer" data block in the XML.

### **6.1 Personal Identification (CNP) vs. Privacy**

The standard identifier for individuals in Romania is the Personal Numeric Code (CNP).

* **Mandatory Reporting:** ANAF requires the identification of the buyer.  
* **The "13 Zeros" Rule:** Recognizing that businesses (e.g., retail, ecommerce) do not always collect the CNP, and that GDPR mandates data minimization, specific derogations exist. For B2C transactions where the CNP is not collected, the system accepts a generic identifier consisting of **13 zeros** (0000000000000) in the Buyer ID field.23  
* **Technical Flagging:** The XML must explicitly indicate the transaction nature. While UBL doesn't have a "B2C flag," this is inferred from the AccountingCustomerParty lacking a VAT registration code and utilizing the personal ID structure.

### **6.2 B2C Endpoints and Logic**

* **Endpoint:** The upload endpoint remains the same (.../upload).  
* **Parameters:** The cif parameter in the URL is *still* the Supplier's CIF (the company issuing the invoice). Do not put the customer's CNP in the URL parameters.  
* **Validation:** The B2C validator rules (active in the test environment since July 2024\) are more lenient regarding address completeness compared to B2B, acknowledging that billing addresses for consumers may be partial.3

## **7\. Testing, Validation, and Operational Resilience**

### **7.1 Validation Strategies**

Before sending to ANAF, applications should perform "Local Validation."

* **XSD Validation:** Validate the generated XML against the UBL 2.1 XSD schema. This catches structural errors (e.g., text in a numeric field).  
* **Business Rule Validation:** Implement a logic layer that checks RO-CIUS rules (e.g., "If VAT rate is 0, Exemption Reason is mandatory").  
* **ANAF Validator Tool:** ANAF provides a JAR file (Java) and an online upload tool that mimics the server-side validation. Integrating the JAR into the CI/CD pipeline or backend processing is a best practice to reduce API failures.24

### **7.2 Handling Rate Limits and Downtime**

The ANAF API is a centralized government service subject to high load, especially on the 25th of the month (tax deadline).

* **Circuit Breaker:** If the API returns 503 Service Unavailable or 504 Gateway Timeout, the application should stop sending requests for a set period (e.g., 5 minutes) and queue them internally.  
* **Asynchronous Processing:** Never make the user wait for the ANAF response in the UI. The "Send to ANAF" button should trigger a background job. The UI should display "Sending..." and update to "Sent" only after the background job confirms the id\_incarcare.

### **7.3 Community Libraries and SDKs**

While a custom implementation is possible, the complexity suggests leveraging existing open-source SDKs where available. Research identifies active libraries for major languages:

* **TypeScript/Node.js:** efactura-anaf-ts-sdk provides typed interfaces for UBL and handles the OAuth flow.11  
* **Go:** printesoi/e-factura-go offers a structured client for the API endpoints.18  
* **PHP:** andalisolutions/anaf-php and pristavu/laravel-anaf provide ready-to-use wrappers for Laravel and general PHP environments.27  
* **C\#/.NET:** RomaniaEFacturaLibrary is available for.NET ecosystems.29

Using these libraries can significantly accelerate development by abstracting the HTTP boilerplate and OAuth token rotation logic.

## **8\. Conclusion and Strategic Recommendations**

The integration with RO e-Factura is a non-trivial engineering challenge that fundamentally alters the architecture of financial software in Romania. It demands a move from isolated systems to a connected, clearance-based ecosystem.

For the developer, success lies in three areas:

1. **Security Rigor:** Correctly managing the OAuth 2.0 lifecycle and securing the long-lived refresh tokens is paramount to preventing unauthorized access to the company's fiscal data.  
2. **Data Precision:** The majority of implementation effort will be spent mapping internal data structures to the rigid RO-CIUS UBL 2.1 format.  
3. **Operational Robustness:** Building a system that assumes the ANAF API will occasionally be slow or unavailable, and handling those states gracefully without data loss.

With the B2C mandate effective January 2025, the volume of data processed by this system will grow exponentially. Architects are advised to design for high scalability, utilizing message queues (e.g., RabbitMQ, Kafka) to decouple XML generation from API transmission, ensuring that the local ERP remains responsive even during peak fiscal reporting periods.

### **Implementation Checklist**

1. \[ \] **Administrative:** Obtain Qualified Digital Certificate & Register in SPV.  
2. \[ \] **Registration:** Register App in ANAF Portal \-\> Get Client ID/Secret.  
3. \[ \] **Auth Module:** Implement OAuth 2.0 (Browser Redirect \+ Token Exchange \+ Refresh Loop).  
4. \[ \] **Data Module:** Map ERP fields to UBL 2.1 RO-CIUS standard. Implement XSD validation.  
5. \[ \] **Core Loop:** Build Async Job: Upload XML \-\> Save Index \-\> Poll Status \-\> Download ZIP.  
6. \[ \] **Storage:** Implement Secure Archive for ZIP files (10 years).  
7. \[ \] **B2C Update:** update XML generation for "13 zeros" CNP logic.  
8. \[ \] **Testing:** Validate B2B and B2C flows in api.anaf.ro/test.  
9. \[ \] **Monitoring:** Set up alerting for 4xx/5xx API errors and Token Expiration.

This roadmap provides the definitive technical path to full compliance with the Romanian e-Factura mandates.
